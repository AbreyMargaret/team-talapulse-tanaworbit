# Application logic — JSON demo

**SI-assisted documentation. All people, PINs, missions, and measurements are fictional.**

## 1. Startup and profile entry

`p-console/src/data.ts` imports the JSON fixtures at build time. `/a-login` compares a public PIN in the browser. `/b-login` compares a public admin or tester code the same way. The crew console does not contact an API to render a profile. `/tester` does call `tanaworbit-api` to recheck the fixtures.

1. `DemoSignIn` lists the four records from `datasets/crew.json`.
2. A profile is preselected; changing the selection clears the input and any prior error.
3. The input accepts up to four digits, from a physical keyboard, native input, or on-screen keypad.
4. When four digits are present, a short 350 ms presentation delay precedes a local string comparison with `demoPin`.
5. A match calls the parent callback, selects that crew member, and opens their dashboard. A mismatch clears the input and announces an error.
6. **Fill demo PIN** fills the intentionally public PIN for the selected profile and follows the same auto-continue flow.

The delay is not server validation. There is no password hashing, protected route, identity verification, token, rate limiter, or security claim. The entire dataset and comparison logic are available in the frontend. Do not enter real credentials.

## 2. Navigation and sign-out

Eight state-selected views are available after demo entry: mission overview, personal dashboard, check-in, trends, exercise/recovery, physiological monitoring, alerts, and guidance.

- Clicking another crew member in Mission Overview returns to the preselected profile on the demo PIN screen. Selecting the currently active crew simply returns to their dashboard.
- Sign out clears the in-memory entry flag and hides the console, but is not a security boundary.
- Temporary check-ins, drafts, exercise additions, and settings remain in the mounted app until refresh, even across demo sign-out/sign-in.
- Refresh starts signed out and restores the original JSON fixtures. There is no persistent session.

The former display shield, inactivity shield, and two-step reveal have been removed. There is no automatic inactivity lock.

## 3. Latest readings and histories

`historyFor(crewId, days)` selects the current mission's example window by `missionDay` and returns ascending mission-day order. Each crew has 30 consecutive synthetic records.

`latestRecord(crewId)` provides the initial latest reading, display-only temperature, and respiration. The current demo mission day is defined in `mission.json`, not the actual calendar date.

Trend charts select 7, 14, or 30 records from this fixture history. Only the current-day point is overridden by the crew's latest in-memory check-in. The earlier points are actual entries in the **synthetic JSON fixture**, not values generated by the chart renderer.

Sparkline decorations and physiological waveform shapes remain illustrative SVG drawings; do not interpret them as sensor traces or exact historical curves.

## 4. Example personal baselines

`personalBaseline(crewId)` computes a separate arithmetic mean for that crew member over the previous `baselineWindowDays` mission days, excluding the current day. The default is 14 days. Each numeric result is rounded to one decimal place.

```text
baseline(metric) =
  roundToOneDecimal(sum(prior synthetic daily values) / number of prior records)
```

Current fixtures yield different baselines per crew member. These are computed **example personal baselines**, not NASA reference ranges, medically validated norms, adaptive models, or learned risk estimates.

The dataset validator requires complete fixture windows. Missing baseline records are treated as a fixture error, not silently replaced with an invented average.

## 5. Demonstration observation rules

Rules come from `monitoring-rules.json`. Comparisons use a strict `>`:

| Observation    | Demo rule                                              |
| -------------- | ------------------------------------------------------ |
| Heart rate     | Absolute difference from example baseline > 10 bpm     |
| Blood pressure | Either component's absolute difference > 10 mmHg       |
| Sleep          | Example baseline minus latest sleep > 1 hour           |
| Fatigue        | Latest self-report minus example baseline > 1.5 points |
| Attention      | Crew profile has the scripted `reviewRequested` flag   |

Observe means that an educational comparison rule matched. Stable means it did not match; it does **not** mean “medically healthy.” Attention demonstrates a review request, not clinical triage. Acknowledging an alert does not clear the underlying scripted crew flag or provide medical clearance.

## 6. Check-ins

- Per-crew drafts live in React state.
- Native number-input constraints and a systolic-greater-than-diastolic consistency check apply.
- Record → Review → Complete requires checking the crew/measurement confirmation box.
- Confirmation replaces the latest in-memory reading and current-day chart point. It does not append a permanent record or mutate the JSON.
- Prior alert-review acknowledgements for that crew member are cleared so updated observations can be reviewed again.
- Body temperature and respiration are fixture-only displays, not fields in the current check-in form.

## 7. Exercise and recovery

`ExercisePanel` reads activity definitions from `exercise-catalog.json` and receives an in-memory copy of `exercise-records.json`.

- A session records activity ID, duration (1–180 minutes), perceived effort (1–10), optional notes, crew/mission IDs, and mission day.
- Selecting an activity fills its editable example duration from the catalog. This is not an exercise prescription.
- Review → Confirm session adds a temporary `manual_demo` entry.
- Today/week totals and bar charts sum durations by mission day. The displayed mean effort is arithmetic, not an exercise-safety score.
- The recovery context reads the **current in-memory health check-in**, so updating sleep/fatigue updates that context.
- The activity log shows latest array additions first and labels JSON fixtures separately from manual demo input.
- No exercise dose, calorie burn, recovery diagnosis, fitness clearance, or sensor-derived result is calculated.

## 8. Exports and limits

CSV export requires explicit review and downloads the current crew's latest health summary. It excludes PINs, notes, exercise logs, historical points, and review acknowledgements. Exporting is the only explicit file-output action; the app never writes to `/datasets`.

Real authentication, shared records, secure storage, device integration, and clinical decision support would need a separate design and validation effort. They are not implemented by this demo.

## 9. Health Toolkit and scripted guide

Measurement walkthroughs navigate to supported check-in fields or the exercise log without recording a value. Body-topic selection groups existing values; it does not generate findings. Context selection changes explanatory text and hazard highlights only; health baseline/rule logic is unchanged. Evidence labels distinguish manual demo overrides, synthetic health fixtures, display-only values, computed example means, and educational sources.

The routine derives check-in completion from the current-run confirmation flag and exercise completion from a current-day `manual_demo` session. Guidance review is a separate per-crew self-acknowledgement. An in-page timer starts while signed in with remaining tasks, supports one/five/fifteen-minute demo intervals or Off, stops on full completion/sign-out, and has snooze/dismiss behavior. It is not reliable after browser suspension or page closure.

Tanaw Guide selects fixed FAQ text with keyword counts, applies a narrow safety-limitation response before topic matching, and fills known template fields from the current demo. Unknown queries use a fixed fallback. No clinical reasoning, LLM/API request, emergency triage, medication advice, or persistent conversation is implemented. Full behavior is in [toolkit-and-guide.md](toolkit-and-guide.md).
